### Module 11 — Property Management — ✅ READY FOR PRODUCTION (2026-09-17, 1 disclosed non-blocking infra exception, 2 out-of-scope follow-ups flagged separately)

**Scope tested**: at the user's explicit request, this module was disambiguated and gated as FOUR sub-planes rather than one narrow slice: `backend/internal/property` (role-context aggregation + rent-passport trust score), `backend/internal/realtor`'s admin control plane and member-facing money plane (lease signing, invoice payment, escrow, marketplace listing browse/search/detail, shortlet booking), and — the largest single piece — `backend/internal/estate` (Estate & Visitor Services: dues/rent billing, vendor jobs/payouts, gate security, visitor access, elections, meetings, facilities, admin console, resident mobile app), which is the single largest backend module in the entire codebase (~156 endpoints) and had never been through any UAT pass before this one. Every row across three formal test-plan docs (`docs/qa/modules/property.md`, `docs/qa/modules/realtor.md`, `docs/qa/modules/estate.md`) plus a purpose-built supplement doc for the money/marketplace planes has a recorded, live-verified outcome — proven via real HTTP calls, real concurrent goroutines, real Postgres SQL, and real GoTrue JWTs, never accepted on a mock or an implementation agent's self-report alone.

**Bugs found**: 18 tracked defects (PROPMGMT-001 through PROPMGMT-018), all closed. Most severe, in order of discovery:
- **PROPMGMT-001** (Blocker) — a tenant could mark their own lease invoice "paid" and activate the lease with zero real money movement, via a directly client-callable Postgres RPC with no wallet debit, no ledger entry, no verification of any kind, reachable in production with no feature flag.
- **PROPMGMT-003/004** (Blockers) — two of the module's sub-planes (the rent-passport IDOR-guarded screening lookup, and estate-property landlord/tenant/transfer-request review) had zero admin UI at all.
- **PROPMGMT-013** (Blocker) — `PayDues` (Estate's dues-collection function) failed on **literally every real payment**: a `VARCHAR(80)` reference column overflowed on every real UUID-based reference, and a partial-unique-index mismatch made the idempotency insert fail with a Postgres error on every attempt, not just duplicates.
- **PROPMGMT-014** (Blocker) — vendor onboarding was completely broken via a SQL placeholder type conflict, making the entire vendor→job→payout chain unreachable in any environment that ever exercised it live.
- **PROPMGMT-015** (Blocker) — a banned or deleted estate member could still read dashboard/profile/invoice data, because two membership-resolution helpers never checked ban/delete status, unlike the module's own primary authz gate.
- **PROPMGMT-016** (Blocker) — the admin console's own resident ban/restore has silently never worked (wrong id sent to the backend), plus five more real type-mismatch/broken-mutation bugs found across the same click-through, all from the identical root cause: service functions calling the live backend against TypeScript types that matched a mock shape, not the real response.
- **PROPMGMT-017** (Blocker, the single most consequential finding of this pass) — the actual Next.js implementation mobile residents use for dues payment (a completely separate code path from the Go `PayDues` fixed earlier in the same pass) had the identical partial-index bug independently: a resident's wallet was genuinely, really debited via a real balanced ledger posting, but the payment record failed to write and the invoice stayed unpaid forever — a resident could be charged real money with no receipt and no record the invoice was ever settled.
- **PROPMGMT-002** (Major) — no escrow-release mechanism existed at all; per the user's explicit choice, built inspection-gated release (a real move-out inspection record gates a real admin-adjudicated payout to either the tenant or the landlord) rather than deferring it.
- **PROPMGMT-011/012** (Major/Minor) — the realtor marketplace listing-detail screen's "Contact agent" button did nothing and "Save listing" never persisted; fixed per the user's explicit choices (phone-reveal, real persistence).
- **PROPMGMT-018** (Major) — the Estate facilities admin page called a nonexistent API route; wired to the real, already-built backend routes.

**Notable findings**: this module is the strongest single demonstration in the entire engagement of why "the code looks complete" is never accepted as proof — Estate alone had a complete, well-written, pre-existing formal test plan and 54 pure-logic test functions, yet had never once been run against a real database, and its two money-moving functions both failed on the very first live attempt. The same "a status flips but the money doesn't move, or moves with no record" failure pattern recurred at least three separate times within this one module (PROPMGMT-001, -013, -017) across three genuinely different code paths (a Supabase RPC, a Go service, and a parallel Next.js implementation of the same feature) — underscoring that this is a systemic pattern worth watching for across every remaining module, not a one-off. Two swarm-coordination incidents (a git-stash mishap that reintroduced an already-fixed regression across 9 unrelated files, and an accidental file deletion between two concurrent remediation agents) were both caught and fully resolved by this session's own independent verification before landing, not left in the final state. Several remediation agents initially responded to a dispatch by delegating to a further sub-agent and reporting a description of intent rather than doing the work themselves — each was caught by requiring real evidence (actual command output, actual HTTP responses, actual SQL results) before acceptance, and corrected to do the work directly.

**Accepted exceptions**: **PROPMGMT-009** — a single leftover, unbalanced test-fixture ledger entry in the shared local dev database, left over from a verification pass; the correct fix (using this codebase's own `PostJournal` primitive, not a raw SQL statement) is fully documented and ready, but the sandbox's own permission classifier twice refused to let this session execute it against the shared database, and the session did not attempt to route around that refusal. Cosmetic — it fails one unrelated global-conservation invariant test for other sessions sharing this database, but does not reflect any defect in shipped code.

**Flagged for separate follow-up, out of this module's scope**: a genuine, severe, platform-wide PII exposure in `user_profiles`' admin-read RLS policy (any authenticated user can read any other user's full profile) — found incidentally, not specific to Property Management, spun off as its own background task. A narrower bug on the Estate facility-detail/"Manage" page (identical dead-route pattern plus a missing backend route) — spun off separately.

**READY FOR PRODUCTION**: Yes. Zero open Blocker or Major defects across all four sub-planes, every test-plan row has a recorded, live-verified outcome, and the one remaining item is an explicitly accepted, non-blocking cosmetic exception.

### Module 13 — Marketplace — ✅ READY FOR PRODUCTION (2026-09-17, 1 disclosed non-blocking scope exception)

**Scope tested**: the general item/service marketplace (`backend/internal/marketplace/`, distinct from the realtor/property marketplace covered under Property Management) — listing lifecycle/moderation, boost purchase/rejection/cancellation money paths, search/discovery pagination, seller management, reviews, and the full 17-page admin console (analytics, taxonomy, CMS, moderation/fraud/users/appeals, pricing). Mature going in relative to this engagement's baseline: a real ledger-backed boost money path (escrow fully retired under ADR-023), 893 lines of pre-existing unit tests, 4,158 lines of pre-existing live-DB integration tests, and a complete formal test plan (`docs/qa/modules/marketplace.md`) — all P0 AUTHZ/FSM/flag-off cases live-executed and confirmed passing.

**Bugs found**: 10 tracked defects (MKT-001 through MKT-010), all closed. Most severe:
- **MKT-002/MKT-008** (Blockers) — `RejectBoost` (admin) and `CancelBoost` (seller-initiated) could both strand a boost permanently unrefunded and un-retriable if the refund step failed (e.g. a seller with no ledger account yet), because the status transition committed as its own write, separate from the refund — independently reproduced twice, from two different angles, by two separate agents before either knew about the other's finding. Fixed with an atomic refund-first-then-single-status-transition pattern, mirroring Estate's own money-path fixes earlier in this engagement, plus resumability for any pre-existing stranded rows.
- **MKT-003** (Blocker) — search pagination was completely non-functional: 5 independently stacked defects across the ES query builder, the client's next-cursor computation, the HTTP handler (which never read `?cursor=` at all — the actual end-to-end root cause), the Postgres fallback path (no `OFFSET` logic whatsoever), and a missing ORDER BY tiebreaker causing real duplicate rows across pages. Fixed and empirically proven via a live 27-listing/6-page sweep with zero duplicates/gaps (versus 2 real duplicates on the pre-fix code).
- **MKT-001** (Major, user-chosen fix) — boost purchase had no tier-limit/KYC gate at all, unlike every sibling money path; closed by reusing Estate's established `TierEnforcer` pattern.
- **MKT-007/MKT-009** — 6 of 17 admin console pages called backend routes that were never implemented, despite their RBAC permission slugs already being seeded ahead of the features they were meant to gate. User chose to build rather than accept as a disclosed gap: real taxonomy CRUD, honest-by-design analytics (fields with no backing data explicitly return 0/null with documented reasoning, e.g. GMV retired under ADR-023), CMS banners/category-content, and a full maker-checker-gated users/appeals/fraud moderation workflow reusing the existing dual-approval primitive from `backend/internal/health/makercheck` (DB-level self-approval block on all 3 new tables, mirroring ADR-005) — live-verified with 3 genuinely distinct admin identities, self-approval correctly 409'd.
- **MKT-010** (Blocker, infrastructure) — a self-discovered, real shared-database migration-chain corruption: a long-dismissed stray migration file had been silently blocking `supabase migration up` for the entire shared local dev database all session, driving several agents toward ad-hoc `psql` patching that desynced tracked migrations from actual schema state and reverted `ledger_accounts`/`mkt_boosts` to an incompatible older shape. Fixed the file's NOT NULL violation, resolved a genuine version collision by renumbering it per this repo's own iron rule, and repaired via the safe, non-destructive `supabase migration up --local` — zero data lost, verified via direct SQL, `go build`, full regression across marketplace + estate suites, and a per-reference ledger-balance invariant (zero unbalanced groups).
- **MKT-005** (Major, investigated not fixed) — a single admin flag-action call returned a false 409 despite the underlying write succeeding; investigated with genuine isolation (a separate worktree, 1,000 single-invocation calls, zero false conflicts) and proven to be correct-as-designed conflict detection, not a code defect — the original report could only be explained by a duplicate client dispatch upstream of this module.
- **MKT-006** (Major) — the pricing admin page's `Promise.all` masked two genuinely working sections behind three missing routes' 404s; same bug shape found repeatedly in sibling modules' consoles this session, fixed with `Promise.allSettled`.

**Notable findings**: this module produced the engagement's first fully self-discovered infrastructure incident (MKT-010) rather than a shipped-code defect — a routine post-batch regression check (re-running suites minutes after personally verifying them passing) caught a real corruption before it could silently propagate further, underscoring the value of re-verification even immediately after a "done" state. Two build-time agent-collision incidents (MKT-009) were both self-caught and correctly resolved by the involved agents before reporting, without any damage to either session's work. Mobile journeys were verified already correctly wired to the real backend — a "chat composer is mocked" theory from discovery was investigated and disproven with precise evidence.

**Accepted exceptions**: the `pricing` admin page's 3 sub-features (commission config, discount codes, featured slots) remain unbuilt — no backing table or business rule exists for them yet, and building them was out of the scope the user approved for this pass. Disclosed, not faked, and gracefully masked (no page crash) by MKT-006's fix.

**READY FOR PRODUCTION**: Yes. Zero open Blocker or Major defects, every P0 test-plan case has a recorded live-verified outcome, and the one remaining item is an explicitly accepted, non-blocking scope exception.

### Module 15 — Pharmacy — ✅ READY FOR PRODUCTION (2026-09-17, 1 disclosed non-blocking scope exception)

**Scope tested**: `backend/internal/health/pharmacy/` — the real clinical/commerce pharmacy vertical (orders, escrow, Rx verification, dispatch, dispense audit). Two distinct "pharmacy" modules exist in this codebase; `backend/internal/pharmacy/` is a thin, standalone catalog+cart module with its own separate QA doc and was NOT this pass's focus. No dedicated formal test plan existed for `health/pharmacy` before this pass — the P0 cases below were derived directly from reading the service/handler code, not from a pre-existing checklist. Real ledger-backed escrow (Hold→Release/Refund) reusing the same rails as Telemedicine/Marketplace, already verified clean this session.

**Bugs found**: 5 tracked defects (PHARMACY-001 through PHARMACY-006, no PHARMACY-005 gap — see below), 4 fully closed, 1 partially closed with a disclosed remainder.
- **PHARMACY-002/003** (Blockers) — `CreateOrder` never wrote to `stock_qty` anywhere, so a product with a small tracked quantity could be oversold without limit (live-reproduced: two concurrent orders both succeeded against a single unit of stock), and any post-hold DB failure (including the new stock-check refusal) left the patient's money stranded in escrow with no order row. Fixed together: an atomic compare-and-swap stock decrement, with the pre-existing but previously-unused `in_stock` column repurposed as the durable "sold out" signal (since `stock_qty=0` is the DB default and today's value for most of the live catalog — a hard floor at 0 would have blocked checkout on the majority of existing products), plus a compensating refund on every post-hold failure path. The fix's own first draft had a real bug (a depleted tracked product was misread as "untracked = unlimited" on the next order) — caught by its own regression test before landing.
- **PHARMACY-004** (Major) — dispatching any DELIVERY-fulfilment order panicked the server (500, nil pointer) because `transport.NewService` was wired with a nil settlement service; the entire DELIVERY lifecycle could never progress past DISPENSED. Fixed by wiring a real settlement service, mirroring `finance_routes.go`'s own established pattern for the identical constructor. Two sibling modules (`health_lab_routes.go`, `health_vet_routes.go`) wire the same constructor with the same nil argument and likely carry the same latent bug — flagged for a check when those modules reach UAT, not fixed here (out of Pharmacy's scope).
- **PHARMACY-006** (Blocker) — the entire pharmacy admin route group, including routes that pre-date this UAT pass, was unreachable with any real token: wired via a helper that applies only a guard checking a context key nothing ever set. Found while building PHARMACY-001's admin fixes. Fixed by wiring real auth middleware, mirroring sibling admin groups' established pattern.
- **PHARMACY-005** (investigated, closed as not-a-defect) — an initially-suspected IDOR on `Complete()` (any caller presenting the pickup code could close someone else's order) was investigated; a code fix was drafted, found to break a pre-existing, deliberately-authored test proving the codebase's actual, tested design is possession-of-the-code as the last-mile handoff credential, not caller identity — reverted before landing rather than silently patched over a real design decision.

**All 8 live-executed P0 cases pass or were resolved**: prescription gating (PASS — correctly enforced both at `CreateOrder` and `Confirm`, defense-in-depth), escrow hold/idempotent replay/cancel-refund/complete-release+commission/delivery-address-requirement (all PASS, verified via direct SQL), IDOR on read/cancel/dispense (PASS).

**Notable findings**: this module produced the clearest example yet in this engagement of a fix agent's own regression test catching a real bug in the fix itself before it ever reached commit (the "depleted tracked product misread as untracked" bug in PHARMACY-002's first draft) — the value of writing the test before trusting the fix, not after. PHARMACY-006 is also notable as a case where an entire pre-existing admin surface (not just this pass's additions) turned out to have never actually worked with a real token in any environment sharing this wiring, found only because the admin-portal build work happened to need a working admin JWT against it.

**Accepted exceptions**: **PHARMACY-001** (remainder) — 6 of the admin console's ~11 presented capabilities (PCN applications, catalog governance, controlled-log, payouts admin, recalls-as-a-list, reporting) have no backing table or service concept anywhere in the backend, a materially larger gap than Marketplace's or Telemedicine's wiring-only admin gaps. Building any of these is a genuine product scope decision (defining what a PCN application review workflow even looks like, for example), not a mechanical fix — disclosed rather than built this pass, pending stakeholder priority input.

**READY FOR PRODUCTION**: Yes. Zero open Blocker or Major defects, every P0 case has a recorded live-verified outcome, and the one remaining item is an explicitly accepted, non-blocking scope exception for admin-console subsystems that don't yet exist anywhere in the backend.

### Module 16 — Laboratory — ✅ READY FOR PRODUCTION (2026-09-17, 2 disclosed non-blocking exceptions)

**Scope tested**: `backend/internal/health/lab/` — the real clinical/commerce lab vertical (test/panel catalog, order lifecycle CREATED→...→RELEASED→CLOSED, chain-of-custody, result entry with a severity-upgrade-only safety backstop, escrow-backed money path reusing the same rails as Telemedicine/Pharmacy). Discovery deliberately checked whether the three bug classes just found in sibling modules (Telemedicine, Pharmacy) reproduced here, given how closely these three verticals share wiring patterns — two of three did.

**Bugs found**: 6 tracked defects (LAB-001 through LAB-007, no LAB numbering gap other than the mixed LAB-001), 5 fully closed, 1 partially closed with a disclosed remainder, plus one disclosed cross-module finding.
- **LAB-002/003/004** (Major/Blocker/Blocker) — three defects found purely by inspection, before any of them were ever hit live, because discovery deliberately went looking for the exact sibling-module bug shapes: a nil settlement service that would have panicked any home-collection dispatch (identical to PHARMACY-004), an admin route group with no real auth middleware that would have 401'd every real admin token (identical to PHARMACY-006), and a SQL uuid/text placeholder-reuse bug in three admin queries that would have broken the instant anyone filtered by a real lab id (the same shape found once already in Pharmacy's own `AdminListOrders`). All three fixed with the exact same patterns already proven in Pharmacy.
- **LAB-005/006** (Major/Blocker) — found live during P0 execution, both in `Handover` (the chain-of-custody phlebotomist→courier handoff): the standard handover step was completely unreachable (a missing state-transition edge), and, independently, the function had no actor/role gate at all — any authenticated caller, including the order's own patient, could reassign custody to an arbitrary party. **All 8 live-executed P0 cases pass**: escrow hold, idempotent create replay (confirmed `CreateOrder`'s idempotency check runs before any gate, unlike Telemedicine's original `BookAppointment` bug), cancel→refund (single, non-double), release→payment+commission (full lifecycle driven to CLOSED, ledger balances to zero), chain-of-custody breach handling (`FlagBreach`→`RECOLLECT_REQUIRED` correctly blocks accession), the result-entry safety backstop (a mis-entered NORMAL correctly upgraded to CRITICAL and escalated, live-confirmed), IDOR on results/custody (403, no partial data leaked even in error responses).

**Notable findings**: this module is the clearest demonstration yet in this engagement that a bug found and fixed in one module is worth deliberately checking for in its close siblings — two of Laboratory's six defects (LAB-002/003) were caught purely by pattern-matching against Pharmacy's just-closed bugs, before either could ever have been hit live, and a third (LAB-004) was caught the same way against a smaller bug inside Pharmacy's own admin fix. LAB-006 is also notable methodologically: a naive regression-guard proof (reverting both Handover fixes together) would have silently missed that the authz gate mattered at all, since the transition-map bug alone produced an error that looked like protection — isolating each fix's revert independently was necessary to actually prove the authz defect.

**Accepted exceptions**: **LAB-001** (remainder) — mlscn-audit, catalog governance, results-audit, phlebotomists-as-an-entity, payouts, and reporting all remain unbuilt in the admin console, none with any backing table or service concept in the backend; a genuine product scope decision, not a mechanical fix, matching Pharmacy's PHARMACY-001 posture. **LAB-007** — the mobile doctor-ordering lab flow is a fully separate, unintegrated shadow system (`doctor_lab_orders`/`doctor_lab_results` in `internal/doctor`, with a hardcoded-empty catalog) that never touches the real `internal/health/lab` module at all; reconciling the two, and then deciding whether referring doctors should get real read access to lab results, is a cross-module architecture decision flagged for dedicated follow-up, not fixed here.

**READY FOR PRODUCTION**: Yes. Zero open Blocker or Major defects, every P0 case has a recorded live-verified outcome, and both remaining items are explicitly accepted, non-blocking exceptions — one a scope decision on unbuilt admin subsystems, the other a cross-module architecture question outside this module's own boundary.
