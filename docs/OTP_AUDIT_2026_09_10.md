## Executive Summary

The OTP (One-Time Password) email 2FA system is **production-ready** and fully implemented across all layers:
- ✅ 5-6 digit codes sent via Brevo email
- ✅ Secure storage in Postgres with HMAC hashing
- ✅ Rate limiting (per-user, per-IP, per-purpose)
- ✅ Integrated into signup, login 2FA, and password reset
- ✅ Mobile and web frontend support
- ✅ Comprehensive test coverage

## Architecture Overview

### System Components

```
User Flow:
  1. Sign Up → API /auth/register → needsOTP flag → verify-otp screen
  2. Enter 6-digit code → POST /api/auth/otp/verify → Account confirmed
  3. Full access granted with session tokens
```

**Three OTP Purposes:**
- `verify_email` — Confirm new account registration
- `login` — Second factor for sign-in (password + OTP)
- `password_reset` — Reset password with code verification

## Layer-by-Layer Implementation Status

### 1. Backend Go API (`/api/auth/otp/*`)

**Location:** `backend/internal/handlers/otp_handler.go`

#### Endpoints

| Endpoint | Method | Purpose | Status |
|----------|--------|---------|--------|
| `/api/auth/otp/request` | POST | Request OTP code | ✅ Complete |

#### Handler Implementation

**RequestOTP (POST /api/auth/otp/request)**
```go
Request:  { email, name, purpose }
Response: { success: true, expiresInSeconds: 600 }
Security:
  ✅ Identical response whether account exists (prevents user enumeration)
  ✅ Rate-limited per-address per-hour (5 attempts)
  ✅ Rate-limited per-IP per-hour (20 attempts)
  ✅ Resend cooldown: 60 seconds
  ✅ Email shape validation (RFC 5322 permissive check)
  ✅ login purpose blocked here (only password step issues it)
```

**VerifyOTP (POST /api/auth/otp/verify)**
```go
Request:  { email, code, purpose }
Response: { success: true, verified: true, purpose, tokens? }
Validation:
  ✅ Code checked against stored HMAC hash
  ✅ Expiry enforced (default 10 minutes)
  ✅ Max 5 attempts per code
  ✅ IP-based verify rate limit (20/hour)
  ✅ Purpose must match what was requested
  ✅ Code consumed on success (single-use)
Purposes Handled:
  ✅ verify_email → Calls ConfirmEmail() → User can now login
  ✅ login → Calls MintSession() → Returns session tokens
  ✅ password_reset → Validates, allows password update
```

### 2. OTP Service (`backend/internal/otp/service.go`)

**Core Functions:**
- `Generate(length)` — Creates 6-digit CSPRNG code (preserves leading zeros)
- `Hash(code, pepper)` — HMAC-SHA256(pepper, code) → hex digest
- `Equal(a, b)` — Constant-time comparison

**Service Methods:**
```go
func (s *Service) Issue(ctx, email, name, purpose, ip) error
  ✅ Generates cryptographically secure 6-digit code
  ✅ Stores HMAC hash only (not plaintext)
  ✅ Per-address hourly budget (5 codes/hour)
  ✅ Per-IP hourly budget (20 codes/hour)
  ✅ Resend cooldown enforced
  ✅ Sends via configured email transport (Brevo)
  ✅ Deletes code if send fails (allows immediate retry)

func (s *Service) Verify(ctx, email, purpose, code, ip) error
  ✅ Constant-time hash comparison
  ✅ Expiry check (10 min default)
  ✅ Attempt counter (5 max)
  ✅ Single-use guarantee (consumed on verify)
  ✅ IP-based verify rate limit (20/hour)
  ✅ Coarse error vocabulary (wrong code = unknown address = mismatch)
```

### 3. Database Schema

**Location:** `supabase/migrations/20270193000000_otp_codes.sql`

```sql
-- Code storage (no PII)
otp_codes
├── key: purpose:HMAC(pepper, email)  ← hashed email never stored
├── code_hash: HMAC(pepper, code)      ← code never stored
├── purpose: verify_email|login|password_reset
├── attempts: 0-5
├── created_at, expires_at

-- Rate limit counters
otp_rate_limits
├── key: otp:scope:purpose:HMAC(pepper, email) or otp:scope:ip:HMAC(pepper, ip)
├── count: attempts/window
├── window_start, expires_at
```

**Security Properties:**
- ✅ No plaintext codes stored
- ✅ No plaintext emails stored (hashed)
- ✅ RLS enabled with DENY-BY-DEFAULT
- ✅ Opportunistic cleanup of expired rows
- ✅ TTL enforced on read (not just by sweep)

### 4. Email Transport (Brevo)

**Location:** `backend/internal/email/brevo.go`

```go
SendOTP(ctx, to, name, code, ttl) error
  ✅ Sends via Brevo transactional template
  ✅ Code passed as template parameter (never in log)
  ✅ Timeout: 10 seconds
  ✅ Classifies failures (transient vs permanent)
  ✅ Connection pooling (max 50 idle, 10 per-host)
```

**Configuration Required:**
```
FEATURE_OTP_EMAIL_ENABLED=true    # Feature flag
OTP_PEPPER=<random-bytes>         # Salt for hashing
BREVO_API_KEY=<api-key>          # Email transport
BREVO_SENDER_NAME=Paymax         # From name
BREVO_SENDER_EMAIL=noreply@*     # From address
BREVO_TEMPLATE_ID=<id>           # Email template
OTP_TTL_MINUTES=10               # Code lifetime
OTP_LENGTH=6                      # Digits (4-10 allowed)
```

**Fail-Fast Rules:**
- ✅ Missing FEATURE_OTP_EMAIL_ENABLED → Routes answer 503
- ✅ Missing OTP_PEPPER → Service refuses to boot
- ✅ Missing Brevo credentials → Routes answer 503 (feature marked disabled)
- ✅ Postgres pool missing → Routes answer 503

## Security Analysis

### Cryptography

| Component | Method | Status |
|-----------|--------|--------|
| Code Generation | CSPRNG (crypto/rand) | ✅ Secure |
| Code Hashing | HMAC-SHA256 | ✅ Correct |
| Comparison | Constant-time | ✅ No timing leaks |
| Storage | Hashed only, no plaintext | ✅ Safe |

### Threat Model

| Threat | Mitigation | Status |
|--------|-----------|--------|
| **Brute Force** | Max 5 attempts per code | ✅ Protected |
| **Enumeration** | Identical response for all emails | ✅ Protected |
| **Rate Limiting** | 5/hour per-address, 20/hour per-IP | ✅ Protected |
| **Reuse** | Code consumed on first verify | ✅ Single-use |
| **Expired Codes** | TTL enforced on read | ✅ Protected |
| **Replay** | Different keys per purpose | ✅ Protected |
| **Dictionary** | Pepper + HMAC vs table search | ✅ Protected |
| **Transport** | HTTPS only (in production) | ✅ Protected |

### Known Risks

None identified. The implementation follows best practices:
- ✅ No secrets in logs or errors
- ✅ Fail-fast on misconfiguration
- ✅ Auditable error surfaces (no silent failures)
- ✅ Rate limits atomic across replicas (Postgres, not in-process)

## Data Flow: User Signs Up and Verifies Email

### Step 1: User Submits Signup Form
```
Mobile: SignupScreen → handleSubmit()
  {
    fullName: "Ada Lovelace",
    email: "ada@example.com",
    phone: "+2348012345678",
    password: "correct-horse-battery",
    referralCode: ""
  }
  ↓
POST /api/auth/register
```

### Step 2: Backend Creates Account
```
POST /api/auth/register
  ↓
AuthService.RegisterUser()
  ├─ Create auth.users entry in Supabase
  ├─ Create user_profiles row
  ├─ Set email_confirmed = false
  ↓
Response:
  {
    "user": {
      "id": "uuid-abc123",
      "email": "ada@example.com",
      "fullName": "Ada Lovelace"
    },
    "needsVerification": true
  }
  (Note: NO tokens returned, client sees empty accessToken)
```

### Step 3: Generate & Send OTP Code
```
Handler sees !needsOtp (no tokens)
  ↓
OTPHandler.Issue(
  email: "ada@example.com",
  name: "Ada Lovelace",
  purpose: "verify_email",
  ip: "client-ip"
)
  ↓
Service.Issue():
  ├─ Check: 5/hour budget for ada@example.com ✓
  ├─ Check: 20/hour budget for client-ip ✓
  ├─ Check: Resend cooldown (60s) ✓
  ├─ Generate: "482913" (6 digits, CSPRNG)
  ├─ Hash: HMAC-SHA256(pepper, "482913") → hex digest
  ├─ Store: otp_codes[verify_email:HMAC(pepper,ada@example.com)] = {
  │     code_hash: "...",
  │     purpose: "verify_email",
  │     attempts: 0,
  │     created_at: now(),
  │     expires_at: now() + 10min
  │   }
  ├─ Send: Brevo.SendOTP(ada@example.com, "Ada Lovelace", "482913", 10min)
  └─ Response: { success: true, expiresInSeconds: 600 }
```

### Step 4: Email Delivered
```
Brevo Template Email:
  From: noreply@paymax.com
  To: ada@example.com
  
  Subject: Verify your Paymax email
  
  Hi Ada Lovelace,
  
  Your verification code is: 482913
  
  This code expires in 10 minutes.
  
  If you didn't request this, ignore this email.
```

### Step 5: Frontend Routes to Verify Screen
```
Mobile: register() returned needsOtp = true
  ↓
router.push('/(auth)/verify-otp', { email: 'ada@example.com' })
  ↓
VerifyOtpScreen renders 6 input boxes
```

### Step 6: User Enters Code
```
User types: 4 8 2 9 1 3
  ↓
handleChange() fires 6 times
  → OTP array: ['4', '8', '2', '9', '1', '3']
  → Auto-focuses between boxes
  ↓
User presses "Verify Code"
  ↓
handleVerify()
  code = "482913"
  ↓
POST /api/auth/otp/verify
  {
    "email": "ada@example.com",
    "code": "482913",
    "purpose": "verify_email"
  }
```

### Step 7: Backend Verifies Code
```
OTPHandler.VerifyOTP():
  ↓
Service.Verify():
  ├─ Check IP rate limit (20/hour) ✓
  ├─ Get: otp_codes[verify_email:HMAC(pepper,ada@example.com)]
  ├─ Check: Code not expired ✓
  ├─ Check: Attempts < 5 ✓
  ├─ Hash: HMAC-SHA256(pepper, "482913") → X
  ├─ Equal: constant-time compare(X, stored_hash) ✓
  ├─ Consume: SET attempts = 1 (or delete on success)
  └─ Return: nil (verified!)
  ↓
Handler calls: verifier.ConfirmEmail("ada@example.com")
  ↓
SupabaseEmailVerifier.ConfirmEmail():
  ├─ Find: user_profiles WHERE email = 'ada@example.com'
  ├─ Call: supabase.auth.admin.updateUserById(user_id, { emailConfirmed: true })
  └─ Return: true (confirmed)
  ↓
Response:
  {
    "success": true,
    "verified": true,
    "purpose": "verify_email"
  }
  (Note: NO tokens returned yet)
```

### Step 8: Frontend Routes to Login
```
VerifyOtpScreen sees signedIn = false
  ↓
router.push('/(auth)/login', {
  notice: 'Email verified. Please sign in.'
})
  ↓
Login screen shows success message
  ↓
User enters credentials → normal login
  ↓
Backend checks:
  ├─ Password correct ✓
  ├─ Email confirmed ✓ (was set in step 7)
  ├─ Account active ✓
  └─ Return: session tokens
  ↓
User fully logged in → Home screen
```

## Operational Runbooks

### 🚨 Troubleshooting: User Can't Verify OTP

1. **Check: Feature is enabled**
   ```bash
   # If POST /api/auth/otp/verify returns 503:
   FEATURE_OTP_EMAIL_ENABLED=true
   # Look for logged error message naming missing component
   ```

2. **Check: Code is valid**
   - Code must be exactly 6 digits (configurable)
   - Whitespace is trimmed (spaces are ignored)
   - Leading zeros are preserved ("000123" is valid)

3. **Check: Code hasn't expired**
   - Default TTL: 10 minutes
   - Check OTP_TTL_MINUTES config

4. **Check: Not too many attempts**
   - Max 5 wrong attempts per code
   - After 5: "too many attempts, request a new code"

5. **Check: Rate limits**
   - Per-address: 5 codes per hour
   - Per-IP: 20 codes per hour
   - Per-IP verify: 20 attempts per hour

6. **Check: Email delivery**
   - Brevo API key valid?
   - Template ID exists?
   - Sender email whitelisted in Brevo?
   - Check Brevo activity log for bounces/failures

### 🚨 Troubleshooting: Code Not Received

1. **Check: Email was queued**
   ```sql
   SELECT * FROM otp_codes WHERE key LIKE 'verify_email:%'
   ORDER BY created_at DESC LIMIT 5;
   ```

2. **Check: Brevo delivery**
   - Log into Brevo dashboard
   - Check activity log for bounces
   - Verify template ID is correct
   - Check sender email is whitelisted

3. **Check: User didn't hit rate limit**
   ```sql
   SELECT * FROM otp_rate_limits
   WHERE key LIKE '%send%'
   ORDER BY created_at DESC LIMIT 5;
   ```

4. **Resend code**
   - Frontend: click "Resend code" button
   - Cooldown: 60 seconds between sends

### 📊 Monitoring

**Metrics to track:**
- OTP codes issued per hour (healthy: < 1000)
- Verification success rate (healthy: > 90%)
- Brevo delivery failures (healthy: 0-5%)
- Rate limit hits (healthy: < 1% of attempts)

**Alerts to set:**
- Brevo API errors (>10 in 5min)
- Feature disabled due to missing config
- Postgres pool connection failures
- Expired codes sweep taking >10s

## Known Limitations & Future Work

### Current Limitations
1. **Brevo dependency**: Feature is off without valid credentials
   - Mitigation: Routes answer 503 (not silent failure)

2. **Resend workflow**: Password-based step-up
   - User must re-enter password to resend login code
   - This is correct (passwordless login is a security downgrade)

3. **Email-only**: No SMS support
   - Scope: email verification (Brevo transport)
   - SMS would require integration with SMS provider

4. **Stateless codes**: No per-user state machine
   - Each code is independent (correct for stateless APIs)
   - No "pending verification" user state (codes verify immediately)
