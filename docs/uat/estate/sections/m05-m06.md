# Estate UAT Gap Analysis — M05 Visitor invitations & access codes · M06 Gate operations & security desk

Source spec: `Estate_Visitor_Access_UAT_Workplan_Test_Cases.md` (20 Oct 2026), §M05 lines 1009–1236, §M06 lines 1237–1345.
Method: read-only inspection of the Go estate backend, the frontend-web `/api/v1/visitor/**` BFF (the channel the React Native Visitor + Guard apps actually call — see `mobile-app/reactnative/docs/visitor/09-ENDPOINT-INVENTORY.md`), Supabase migrations, and the RN `app/visitor` + `app/guard` surfaces. No code was modified.

**Architecture note (drives many verdicts):** visitor/gate functionality exists in TWO channels:
1. **Go backend** — `backend/internal/app/finance_routes.go:1187–1378` wired to `backend/internal/estate/{handler,service}.go`. Server-side validity/usage enforcement is largely here, but authorization is only "estate member" (`assertResident`), not a distinct gate-officer role.
2. **Next.js BFF** — `frontend-web/src/app/api/v1/visitor/**` backed by tables from `supabase/migrations/20260622000500_visitor_gate_extended.sql`. This is what the mobile Visitor and Guard screens call. Guard authorization = an active `gate_sessions` row (`frontend-web/src/server/visitor/gate.service.ts:9–27`), but **no route anywhere creates a gate session** (only GET `/gate/session`, `:8–28`), and admit/deny/exit routes **do not re-check status/expiry/uses server-side**.

### Cross-cutting security-invariant verdicts (the doc's emphasized invariants)
- **Code expiry / single-use / max guests / revoked**: enforced server-side only on the Go channel (svc:374–378, denyReason 582–599). The mobile/BFF guard channel (routes/gate/approve|exit|checkout) performs **no status/expiry/usage re-validation** → P0 blockers for 0079–0083, 0094.
- **Gate/estate binding**: estate binding ✅ everywhere; gate binding ❌ nonexistent (0086).
- **Offline revocation**: ❌ no revocation feed, no offline mode (0106–0107); offline logs are stored but never applied (0108–0109).
- **Cross-estate isolation**: ✅ strong (estate-scoped queries + uniform 404s; RLS + service-role BFF scoping in code).
- **Guard role checks (server-side)**: ❌ Go accepts any estate member for guard actions (0105); BFF requires a gate session that cannot legitimately be created (0101); no supervisor role for overrides (0104).

### Top 5 highest-severity gaps
1. **S1 — Mobile guard admit path performs no server-side validation of expired/used/revoked codes or max_uses** (routes/gate/approve/route.ts:26–57; increments of `used_count` absent) — breaks 0079, 0080, 0081, 0082, 0083, 0094, 0115 on the primary channel; enforcement today is client/mock-only (visitor.api.ts:197–211; LookupOutcome.kind never computed by the server — live lookup returns `{found,code,blacklisted}` (gate/lookup route:38,53), which also mismatches the client contract used by guard/confirm/[code].tsx:179–194).
2. **S1 — No way to start a guard shift**: `gate_sessions` is read-only (session route GET only; zero insert paths repo-wide) → entire M06 mobile channel unusable without seeded DB rows; 0101, 0111 blocked at the gate (and device binding, 0110, has no substrate).
3. **S1 — Guard role/permission checks absent server-side on the Go estate API** (`assertResident` gates all /guard/* writes, svc:391–394,446,467,484,539) — any resident can check in/out visitors, file incidents and forge offline logs; violates §4.2 "Validate code/check in = Gate only, gate-device enrollment required".
4. **S0/S1 — Resident arrival-approval workflow (accept/decline/timeout) entirely missing** (arrival = notification only, routes/codes/[id]/arrival/route.ts:52–60) — 0088/0089/0090 untestable; guard can always admit.
5. **S1 — Offline story is storage-only**: no device-side offline mode or cached-credential validation (no NetInfo/AsyncStorage in guard code), BFF sync is a status flip, Go offline logs never materialize to presence; revocations never reach devices (0106–0109). Honorable mentions: unsigned QR + weak `Math.random` 6-digit codes with no rate limiting (0070/0095/0103), no code regeneration (0084), no gate binding (0086), former-resident codes still valid (0098), no max-validity/quota policies (0077/0078), no visitor PII retention purge (0097).
