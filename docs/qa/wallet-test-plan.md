# Wallet Module — UAT Test Plan

Module 7 in the fixed 21-module go-live queue. Built fresh (unlike Contest, this module had no pre-existing test-plan artifact) from Phase 1 discovery findings — see the discovery notes folded into §0 below.

Status legend: ✅ Pass · ❌ Fail · 🚫 Missing · ⚠️ Blocked · 🚧 Partial · 🔧 Fixed · 🏗️ Built · ⬜ Not Run

## 0. Discovery summary (Phase 1)

- **Backend home**: `backend/internal/finance/wallet/` — thin (balance + transaction listing only). Top-up, PIN, and wallet-to-wallet transfer live in `frontend-web/src/server/wallet/` and `backend/internal/finance/transfers/`.
- **Unified ledger plane**: ADR-045 (one wallet plane) and ADR-051 (FX NGN single wallet) confirmed live in current code, not aspirational.
- **Card rail**: ADR-041 (card tops up wallet, waits for webhook credit before charging) confirmed live.
- **Top-up verify fallback**: `frontend-web/src/server/wallet/verify.ts` self-heals pending Paystack intents on read (handles the "webhook can't reach localhost" dev gap) — fails closed on ambiguity.
- **PIN-UI gap RESOLVED (Phase 3)**: found elsewhere, not missing. `mobile-app/reactnative/app/security/set-pin.tsx` is a full set/change-PIN screen wired to `getPinStatus`/`createPin`/`verifyPin` (`src/features/transfers/api.ts` → `GET/POST /api/v1/transfers/pin*` → Go `backend/internal/finance/transfers/handler.go` `PinStatus`/`SetPin`/`VerifyPin`, backed by `pin.go`'s bcrypt+lockout `user_transaction_pin` store). It was missed by a plain `app/wallet/` or bare-word grep because (a) it lives under `app/security/`, not `app/wallet/`, and (b) it is enforced as an app-wide **root-layout gate** (`app/_layout.tsx`), not a per-screen button: a signed-in user with no PIN is redirected to `/security/set-pin` the moment they navigate toward any route in `src/features/security/moneyRoutes.ts`'s money-route table (wallet, transfers, crypto, stocks, checkout steps, etc.), and Profile → Security → "Change transaction PIN" reaches the same screen in `mode=manage`. See WJ-007/WJ-008 below for full evidence. **However**, Phase 3 found a real, more severe gap in the same area: the two primary debit screens (`app/wallet/send.tsx`, `app/wallet/withdraw.tsx`, both backed by `PaymentActionScreen.tsx`) called transfer/withdraw APIs that never sent a PIN at all, and the server-side handlers never checked for one — see **WAL-006** (fixed) in §7.
- **RBAC**: wallet reuses Finance-wide `finance:adjust:initiate`/`finance:adjust:approve` (maker-checker) and Go's `finance.admin.transfers` — no wallet-specific permission exists.
- **Admin surface**: `frontend-admin/app/admin/finance/wallets/page.tsx` — balance + ledger lookup only, no manual adjustment UI on this page (adjustments live on the separate Finance-wide `/admin/payments-finance` maker-checker console).

### WAL-003 — Admin RBAC permission check silently used a stale JWT role instead of the live DB role for every real (Bearer-token) caller — FIXED
- **Description**: `assertAdminPermission()` (`frontend-web/src/server/admin/auth.ts`), the single gate in front of ~28 admin routes across the whole platform (not just wallet), is documented as "Role from DB is the source of truth; user_metadata is only a fallback." In practice, for every caller using `Authorization: Bearer <token>` — which is how the real `frontend-admin` console actually calls it (`localStorage` token, cross-origin from port 3001 to 3000, confirmed by reading `paymentsFinanceAdminService.ts`'s `authHeaders()`) — the DB lookup silently returned zero rows and the check fell through to the JWT's `user_metadata.role`, which is whatever was set at account-creation time and is never updated afterward.
- **Root cause**: `createClient()` used for the profile lookup is the cookie/RLS-scoped Supabase client. A Bearer-token caller never sets that client's session (only `supabase.auth.getUser(token)` was called, which validates the JWT but does not authenticate the client itself), so `SELECT role FROM user_profiles WHERE id=...` ran as an anonymous request. `user_profiles`' own-row-only RLS SELECT policy (`auth.uid() = id`) then silently matched zero rows instead of erroring, and the code's fallback chain (`profile?.role || app_metadata?.role || user_metadata?.role`) picked up the stale JWT value with no error or log to signal the DB path never actually ran. **Reproduced directly**: updated `user_profiles.role` to `'finance_admin'` in the DB for a test admin, then called the wallet-adjust route with that admin's Bearer token — got `403 Forbidden`. Decoded the JWT and found `user_metadata.role: "admin"` (stale, from account creation) being used instead, mapping via `parseAdminRole`'s alias table to `super_admin`, which does NOT have `finance:adjust:initiate` — an unrelated, contradictory-looking 403 that had nothing to do with the actual DB role.
- **Impact**: Any `user_profiles.role` change — granting OR revoking finance/admin access — is a no-op for every real Bearer-token admin caller until their JWT is reissued with fresh metadata (which nothing in this codebase does automatically). This blocked accurate testing of WA-002/WA-003/WA-004 until fixed, and independently is a correctness/security-hygiene bug in its own right (role changes not taking effect is the dangerous direction for a revoke).
- **Fix**: `frontend-web/src/server/admin/auth.ts` — the `user_profiles.role` lookup now uses `createAdminClient()` (service-role, bypasses RLS — already existed in the same file/module for other purposes) instead of the cookie-scoped `createClient()`. `getUser(token)` still uses the cookie-scoped client purely to validate the JWT. One-line-of-intent change, ~10 lines including the explanatory comment.
- **Test**: Live HTTP re-verified after the fix: same `finance_admin`-role admin, same Bearer token → `200`, wallet credit executed and DB-confirmed. RBAC negative case re-verified: `content_manager` role → `403`. Existing unit suite `tests/unit/voting/sec-002-rbac-scoping.spec.ts` (SEC-002, a DIFFERENT module's RBAC test that happens to exercise this same shared function) broke against the fix because its mocks only wired `createClient`, not `createAdminClient` — updated the test's `mockSupabaseUser()` helper to mock both identically (the assertion logic itself is unchanged; this is a mock-wiring fix, not a weakened test). All 7 cases in that file pass again.
- **Status**: Fixed and verified. `cd frontend-web && npx vitest run` — 1011/1015 passing (the 2 pre-existing unrelated `tests/unit/utility/routes.spec.ts` failures the task flagged as acceptable, plus 1 skipped/1 todo, unchanged); `npx tsc --noEmit` clean.
