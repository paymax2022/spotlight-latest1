# Refer & Earn — UAT Test Plan

Module 8 in the fixed 21-module go-live queue. Built fresh from Phase 1 discovery findings (see §0 below) — no pre-existing test-plan artifact for this module.

Status legend: ✅ Pass · ❌ Fail · 🚫 Missing · ⚠️ Blocked · 🚧 Partial · 🔧 Fixed · 🏗️ Built · ⬜ Not Run

## 0. Discovery summary (Phase 1)

Three independent, simultaneously-live referral/reward implementations exist, not the "two systems" prior session memory suggested — that note **understated** the situation:

- **System A** ("§7A Referral Earning core") — `backend/internal/referral/*` (13 subpackages). Mounted `/api/finance/referral/*` (member), `/api/referral/admin/*` (admin). Flag: `FeatureReferralsEnabled`.
- **System B** ("Direct Referral Rewards Engine", newer, supersedes A per its own comments) — `backend/internal/finance/referrals/*`. Mounted `/v1/referrals/*` (member), `/v1/admin/referrals/*` (admin), `/internal/referrals/*` (webhooks). Flag: `FeatureReferralRewardsEnabled`.
- **System C** (Next.js-native, tied to vote-bridge) — `frontend-web/src/server/referrals/{service,attribution}.ts` — a flat ₦500 reward triggered when a referred user casts a vote, via `bridge_outbox` events.

**Both A and B are simultaneously enabled** in this environment. `referral_attributions` (System A's table) is correctly shared/reused by System B's migration — not duplicated. Three code-storage surfaces exist: `finance_referral_codes` (legacy/System C), `referral_links` (System B's canonical table, explicitly documented as distinct from the legacy seed), and System A's resolver only ever reads the legacy table.

Admin reporting/management is extensive for System A (`frontend-admin/app/admin/referral/**`) and System B (`frontend-admin/app/admin/referral-rewards/**`) — NOT a Blocker-severity gap, contrary to the default assumption. System C's ₦500 vote-triggered reward has no admin visibility anywhere found — a real, narrower gap (see REF-007).

Full findings, file:line citations, and money-path analysis are in the Phase 1 discovery report (summarized into REF-001 through REF-007 in §7 below).

## 7. Defect log

### REF-001 — Vote-triggered referral reward has a silently-stubbed duplicate handler in the outbox drain path — FIXED
- **Description**: Two independent consumers drain `bridge_outbox` rows with `event_type='referral.triggered'`: `frontend-web/app/api/v1/referrals/outbox/route.ts` → `processReferralOutbox()` (real credit), and `frontend-web/src/server/voting-bridge/outbox.ts`'s `processPendingOutboxEvents` → `handleReferralTriggered()`, which was a literal `// TODO: Implement referral reward logic` stub that logged and returned `true` — marking the row `done` without crediting anyone. Confirmed live: neither drain path is actually wired to a cron/scheduler anywhere in the repo today, so this was a live trap for the first ops wiring rather than a currently-firing incident — but the risk was real and unrecoverable the moment either path got scheduled.
- **Root cause**: A second, generic outbox-draining worker was built for the vote-bridge with a stubbed referral handler, never wired up to the real credit logic built separately in `referrals/service.ts`.
- **Fix**: `handleReferralTriggered()` now calls the real `processReferralReward()` (the same function `processReferralOutbox()` uses) instead of stubbing out — both drain paths converge on one implementation. A malformed payload (missing `shareCode`/`voterId`) is marked done rather than retried forever; a thrown error returns `false` so the caller's existing retry logic applies.
- **Test**: New `tests/unit/voting-bridge/outbox-referral-convergence.spec.ts` (5 tests, in-memory) + `tests/integration/referrals/outbox-referral-live.test.ts` (2 tests, real local Postgres). **Live SQL proof**: a real `bridge_outbox` row drained through the fixed function produced exactly one `CREDIT` ledger row (₦500, correctly keyed idempotency key) and the outbox row correctly marked `done`; a duplicate row drained through BOTH paths still produced exactly one credit, never two. `npx vitest run`: 1077/1081 (same 2 pre-existing unrelated failures, zero new). `npx tsc --noEmit` clean.
- **Status**: Closed.

### REF-002 — System A's attribution resolver never sees codes minted by System B's canonical table — FIXED
- **Description**: System B's `resolveCode()` (`rewards_service.go`) correctly checks `referral_links` then falls back to `finance_referral_codes`. System A's attribution resolver (`attribution/service.go`) was wired to System B's OLDER `Service.ResolveCodeToReferrer`, which only queried `finance_referral_codes` — never `referral_links`. A code issued by the newer engine was invisible to System A's signup attribution, routed to the house account with a false "invalid code" risk flag.
- **Root cause**: System A was wired to an older resolver method that predates System B's `referral_links` table.
- **Fix**: New `RewardService.ResolveCodeToReferrer()` adapter in `rewards_service.go`, wrapping the already-correct private `resolveCode()` to satisfy the `CodeResolver` interface. Both wiring sites in `referral_routes.go` (`newAttributionService`, `RegisterReferral`) now construct `referrals.NewRewardService(...)` instead of the legacy `referrals.NewService(...)` — a drop-in swap, no duplicated lookup logic.
- **Test**: New live-DB tests in `rewards_service_test.go` and a new `attribution/resolve_code_live_test.go` — all passing against real Postgres (with and without `-race`), independently re-run by the orchestrating session. **Live before/after proof**: with the fix stashed, a code minted only into `referral_links` resolved to `is_house=true, risk_flag="invalid_code"`; with the fix restored, the same code resolved to the correct real referrer with no risk flag. Confirmed the reverse case (a legacy-table-only code) still resolves correctly, and a genuinely nonexistent code still correctly routes to the house. `go build`/`go vet` clean.
- **Status**: Closed.

### REF-003 — 8 System A member routes unreachable due to a double route-group mount — ALREADY FIXED (Phase 1 discovery false positive)
- **Description**: `backend/internal/app/referral_routes.go` carries a comment (around lines 99-103) explaining that grouping `/referral` again would have mounted 8 member routes at `/api/finance/referral/referral/*` instead of `/api/finance/referral/*`. Phase 1 discovery misread this as a live, uncorrected bug.
- **Correction**: The comment is historical documentation of a fix already applied in commit `848d0892` ("fix(referral): mount member routes at the path clients actually call"), which was already an ancestor of this branch's HEAD before this UAT pass began. The current code reads `mg := member` (not `member.Group("/referral")`), exactly matching the pattern the comment describes as correct. **Live-verified**: all 8 routes respond correctly at their short path on a throwaway backend instance; the old doubled path correctly 404s with nothing listening there; the `[GIN-debug]` route-registration log shows each route mounted exactly once, at the correct path. No client (web or mobile) was found calling the doubled path either.
- **Status**: Closed — not a defect, discovery error corrected.

### REF-004 — Two different referral-code generators write incompatible formats into the same table — FIXED (with REF-008)
- **Description**: `finance_referral_codes.code` was populated by `backend/internal/finance/referrals/service.go` (Go: 8 lowercase hex chars) OR `frontend-web/src/server/referrals/service.ts` (Next.js: `SPOT-XXXXXX`, 6 chars from a curated alphabet), depending on which stack created the row first. No shared format contract.
- **Root cause**: Two independent implementations writing to the same legacy table without a shared code-generation contract.
- **Fix**: Both generators now produce the identical shape — reused System B's own existing, well-designed convention for its canonical `referral_links` table (`code.go`'s `codeAlphabet`, 5 chars, uppercase, confusable-characters explicitly excluded — the same format already chosen deliberately because "a referral code is read aloud and typed by hand"). Go's legacy `generateCode()` was removed entirely in favor of calling the same-package `GenerateCode()`; the Next.js generator was rewritten to the identical alphabet/length/case, dropping the `SPOT-` prefix. Live-verified: both stacks now produce codes of the same shape (e.g. `FQ9FJ` from Go, `BJC3U` from Node).
- **Test**: 3 new live-DB tests in `rewards_service_test.go` proving format consistency; `referrals-service.spec.ts` extended with a `generateCode` shape/alphabet test.
- **Status**: Closed.

### REF-005 — Zero test coverage for the actual money-crediting logic in Systems B and C — FIXED
- **Description**: No test file existed for `rewards_service.go`'s `OnPurchaseSettled`, `OnPurchaseRefunded`, `RecalculateTiers`, `AdjustCase`, or milestone awarding. Zero tests existed for `frontend-web/src/server/referrals/service.ts` or `attribution.ts` (System C's ₦500 credit path).
- **Fix**: New `backend/internal/finance/referrals/rewards_service_test.go` (11 live-DB tests: happy-path credit, fractional-kobo truncation, idempotent replay, no-attribution/self-referral/non-positive-margin no-ops, refund reversal + its own idempotency, refund-on-non-CREDITED no-op) and new `frontend-web/tests/unit/wallet/referrals-service.spec.ts` (11 tests: correct credit/idempotency-key shape, replay no-op, code resolution normalization, attribution success/idempotent/self-referral/invalid-code paths). No new bugs found in either path — both behaved exactly as documented under test (floor-truncation, idempotency, fail-closed self-referral). All tests passing, including `-race`. ### REF-008 — Legacy referral codes are unresolvable through attribution due to a case-sensitivity mismatch (found while fixing REF-002) — FIXED (with REF-004)
- **Description**: `finance/referrals/service.go`'s `generateCode()` produced lowercase hex codes, but `attribution.normalizeCode()` uppercases the input before lookup — so a legacy code issued via the live `GET /finance/referrals/me` endpoint was unresolvable through signup attribution, independent of and in addition to REF-002.
- **Root cause**: The two functions were written with inconsistent case conventions and never reconciled.
- **Fix**: All new codes are uppercase-only going forward (REF-004's fix). For already-issued codes stored in any case, resolution is now case-INSENSITIVE at every read site: `finance/referrals/service.go`'s `ResolveCodeToReferrer` (`WHERE UPPER(code) = UPPER($1)`), `RewardService.resolveCode`'s legacy-table fallback (same pattern), and the Next.js `resolveCodeToReferrer` (`.ilike()`, with a new `escapeLikePattern()` helper so `%`/`_`/`\` in a code can't behave as ILIKE wildcards). A new additive migration adds a case-insensitive unique index (`UPPER(code)`) so a case-insensitive resolver can never face two different-case duplicates of "the same" code. `referral_links` (System B's own table) was deliberately left untouched — it already generates uppercase-only, consistently.
- **Test**: New live-DB tests proving case-insensitive resolution through both the legacy `Service` and the production-wired `RewardService`; a new case-mismatch regression test and an ILIKE-wildcard-escaping test on the TS side.
- **Status**: Closed.

### REF-009 — A suspended/closed referrer's account can still receive a real referral-reward payout (found executing RE-006) — PARTIALLY FIXED (withdraw gate added, root cause left open by design)
- **Description**: Accrued a real referrer reward (`referral_reward_ledger.state='earned'`), set `platform_users.status='suspended'` for that referrer, then drove the reward through the real `earned→pending→vesting→eligible→paid` transition path. The payout succeeded anyway: `state` flipped to `paid`, and the referrer's wallet balance moved from 0 to a real, posted 50,000-kobo credit — into a wallet belonging to a suspended account.
- **Root cause**: No account-status check exists anywhere in the money-crediting path. This is NOT referral-specific — `finance/ledger.Service.Credit()` is the shared money-crediting primitive used across many modules, so accrual/payout still proceeds for a suspended account by design of this batch's fix — deliberately NOT changed at that layer (mirrors the WAL-005 precedent: app-wide blast radius outside this batch's authority) and there remains a genuine open design question (block receiving credits entirely, or only withdrawing them?) this engagement can't resolve unilaterally.
- **Fix (narrowly scoped, as planned)**: `backend/internal/referral/ledger/service.go`'s `WithdrawEligible` now calls a new `checkAccountEligibleForWithdrawal()` gate — a suspended, locked (including an indefinite `locked_until IS NULL` lock), or deleted `platform_users` account is refused a WITHDRAWAL request, mirroring `auth_service.go`'s existing `validateLoginStatus` status/lock semantics exactly. `Transition`/`Credit` (the accrual/payout primitives) are untouched, as scoped. `handlers.go` maps the new `ErrAccountNotEligible` to HTTP 403.
- **Test**: New `TestWithdrawEligible_AccountStatusGate_Integration` (4 sub-cases: suspended, indefinitely locked, lock already expired, active) — all passing against real Postgres including `-race`; pre-existing `WithdrawEligible` tests (legitimate path, KYC gate) confirmed unaffected.
- **Status**: Partially closed. Withdrawal is now blocked for a suspended/locked/deleted referrer; the underlying accrual/payout-side gap remains open by design, pending a cross-module product decision on the shared ledger's crediting semantics.

### REF-010 — `referral_events` (System C's audit trail) has no DB-level immutability enforcement (found executing RC-003) — FIXED
- **Description**: Unlike `ledger_entries` (which has `ledger_entries_no_truncate` and `ledger_entries_no_update_delete` triggers), `referral_events` had zero triggers — confirmed via direct query against `pg_trigger`. Nothing at the DB level stopped an UPDATE or DELETE via the service-role connection the app always uses; "durable" was asserted by convention/code discipline, not enforced by the database.
- **Root cause**: The migration creating `referral_events` never added the same immutability triggers `ledger_entries` has.
- **Fix**: New additive migration `20270217000000_referral_events_immutable.sql` adds a new `referral_events_immutable()` trigger function (a fresh function, not a reuse of `ledger_entries_immutable()`, since that one's error message is hardcoded to name `ledger_entries` specifically) plus the same BEFORE UPDATE/DELETE row trigger + BEFORE TRUNCATE statement trigger pattern.
- **Test**: Live-verified against real Postgres: a real INSERT still succeeds; a real UPDATE and DELETE on that row both now fail with a clear, table-appropriate error (`"referral_events is append-only: UPDATE/DELETE is not permitted on a posted referral reward"`), matching `ledger_entries`'s error shape/`ERRCODE`.
- **Status**: Closed.

### REF-011 — `ClawBack` on an already-paid reward never reversed the wallet credit (found executing RA-004's live-mode verification) — FIXED
- **Description**: `backend/internal/referral/ledger/service.go`'s `ClawBack()` just called `Transition(ctx, rewardID, StateClawedBack, idempotencyKey)`. `Transition()` only ever posted money when the TARGET state was `paid` — there was no branch posting a reversal when clawing back a reward whose CURRENT state was already `paid`. Live-reproduced: seeded a real reward through a genuine `pending→vesting→eligible→paid` transition (a real 45,000-kobo credit posted), called `ClawBack` on it — `referral_reward_ledger.state` flipped to `clawed_back` and an audit event recorded, but the wallet balance stayed at 45,000 kobo and no reversing entry existed. The system believed money was recovered when it demonstrably was not. The function's own doc comment ("For a real prior payout it posts a reversing entry") and the admin UI's confirmation copy both described the correct behavior — it just was never implemented.
- **Root cause**: `Transition()`'s money-posting logic only had a forward (payout) branch, never a reversal branch for the `paid→clawed_back` transition.
- **Fix**: `Transition()` now posts a balanced reversal via the shared `financeledger.Service.PostReversal()` whenever `current == StatePaid && nextState == StateClawedBack` for a non-house reward with a real beneficiary — draining the beneficiary's wallet and restoring the standing referral-reward account. The reversal's idempotency key is derived from `rewardID` alone (`"referral:clawback:"+rewardID`), distinct from the payout's own key, so a replayed clawback is always a safe no-op and can never collide with the original credit's key.
- **Test**: New `clawback_integration_test.go` — `TestClawBack_PaidReward_PostsBalancedReversal_Integration` (reversal posts correctly, replay is idempotent) and `TestClawBack_NotYetPaidReward_StateOnly_NoReversal_Integration` (a not-yet-paid clawback stays state-only, no regression). Both pass against real Postgres including `-race`. **Live before/after proof**: before, balance stayed 45,000 kobo after clawback, zero new ledger rows; after, balance returns to 0 via a real balanced `REVERSAL_DEBIT`/`REVERSAL_CREDIT` pair.
- **Status**: Closed.

### REF-012 — Two admin pages crashed in live mode on a response-envelope mismatch (found alongside REF-011) — FIXED
- **Description**: `frontend-admin/src/services/referralAdminOpsService.ts`'s generic `getJson()` helper assumed every backend response wraps its payload in a `data` field (`j?.data ?? j`). `backend/internal/referral/risk/handlers.go`'s review-queue and clawbacks list endpoints instead return `{"items": [...]}` and `{"clawbacks": [...]}` respectively — so `getJson()` returned the whole envelope object as if it were the array, and `rows.map(...)` crashed with `rows.map is not a function`. Live-reproduced: both `/admin/referral/risk/review-queue` and `/admin/referral/risk/clawbacks` crashed to a full-page Next.js runtime error in live (non-fixture) mode.
- **Root cause**: `getJson()`'s generic envelope-unwrap assumption didn't hold for these two specific endpoints.
- **Fix**: `listClawbacks()` and `listReviewQueue()` now fetch directly and unwrap the actual field each endpoint returns (`body.clawbacks`, `body.items`) instead of going through `getJson()`. `getJson()` itself was deliberately left unchanged, to avoid affecting any other call site that might genuinely receive `{data: ...}`.
- **Test**: Live-verified on throwaway `frontend-admin`/Go backend instances (never touching shared `:3001`/`:8091`): with the fix, both pages render real seeded rows with no console errors; reverting just these two functions reproduced the exact original crash, confirming the fix is what resolves it.
